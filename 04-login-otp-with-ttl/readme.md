# Login OTP with TTL

This project is a small Express and Redis application that demonstrates how to
generate a six-digit one-time password (OTP), store it in Redis with an
expiration time, verify it, and inspect its remaining time-to-live (TTL).

The OTP is stored for **30 seconds**. After it expires, Redis automatically
removes the key and the OTP can no longer be verified.

## What has been done

- Created an Express HTTP server.
- Added JSON request-body parsing with `express.json()`.
- Added URL-encoded request-body parsing with `express.urlencoded()`.
- Added `ioredis` as the Redis client.
- Configured Redis with the `REDIS_URL` environment variable.
- Added the default Redis URL `redis://localhost:6379`.
- Created a reusable `otpKey()` function for consistent Redis key names.
- Generated a random six-digit OTP.
- Stored each OTP in Redis with a 30-second expiration.
- Added an endpoint to request an OTP.
- Added an endpoint to verify an OTP.
- Deleted the OTP after successful verification so it can only be used once.
- Added an endpoint to check the remaining OTP TTL.
- Configured the application to run on port `3000`.
- Used ES module syntax through `"type": "module"` in `package.json`.

## Redis key design

The application stores an OTP under a key generated by this pattern:

```text
otp:<phone-number>
```

For example, an OTP for `9876543210` is stored as:

```text
Key:   otp:9876543210
Value: 123456
TTL:   30 seconds
```

Using a helper function for the key keeps the key format consistent across the
create, verify, and TTL endpoints:

```js
function otpKey(phoneNumber) {
    return `otp:${phoneNumber}`;
}
```

## How OTP generation works

The application generates a six-digit number with:

```js
Math.floor(100000 + Math.random() * 900000)
```

The generated number is stored in Redis with the `EX` option:

```js
await redis.set(genKey, otp, "EX", 30);
```

`EX 30` tells Redis to expire the key after 30 seconds. Requesting another OTP
for the same phone number uses the same Redis key and replaces the previous
OTP, starting a new 30-second expiration period.

## Install and run

### 1. Start Redis

Redis must be running on port `6379`. From the project root, the included
Docker Compose file can start the local Redis service:

```bash
docker compose up
```

The Docker Compose configuration exposes Redis at:

```text
redis://localhost:6379
```

### 2. Install project dependencies

From this directory:

```bash
cd 04-login-otp-with-ttl
npm install
```

### 3. Start the application

```bash
npm run dev
```

The API runs at:

```text
http://localhost:3000
```

The `dev` script runs `node src/index.js`.

## Environment variable

The application supports:

```text
REDIS_URL
```

If `REDIS_URL` is not set, the application uses:

```text
redis://localhost:6379
```

To use a different Redis server:

```bash
REDIS_URL=redis://localhost:6379 npm run dev
```

## API endpoints

### Request an OTP

```http
POST /otp
```

Request body:

```json
{
  "phone": "9876543210"
}
```

Example:

```bash
curl -X POST http://localhost:3000/otp \
  -H "Content-Type: application/json" \
  -d '{"phone":"9876543210"}'
```

Example response:

```json
{
  "message": "OTP sent to 9876543210",
  "otp": 123456
}
```

The endpoint:

1. Reads `phone` from the request body.
2. Builds the Redis key `otp:<phone>`.
3. Generates a random six-digit OTP.
4. Stores the OTP in Redis for 30 seconds.
5. Returns the OTP in the response.

In a real login system, the OTP should be sent through an SMS or email
provider. This example returns the OTP only to make local testing easy.

### Verify an OTP

```http
POST /otp/verify
```

Request body:

```json
{
  "phone": "9876543210",
  "otp": "123456"
}
```

Example:

```bash
curl -X POST http://localhost:3000/otp/verify \
  -H "Content-Type: application/json" \
  -d '{"phone":"9876543210","otp":"123456"}'
```

Successful response:

```json
{
  "message": "OTP verified !!"
}
```

The endpoint:

1. Reads the OTP stored at `otp:<phone>`.
2. Returns `"OTP does not exist!"` if the key has expired or does not exist.
3. Compares the stored OTP with the OTP supplied by the client.
4. Returns `"Wrong OTP!!"` when the values do not match.
5. Deletes the Redis key after a successful match.

The OTP is therefore single-use. A second verification attempt with the same
OTP returns `"OTP does not exist!"` after the first successful verification.

Expired or missing OTP response:

```json
{
  "message": "OTP does not exist!"
}
```

Incorrect OTP response:

```json
{
  "message": "Wrong OTP!!"
}
```

### Check the remaining TTL

```http
GET /otp/:phone/ttl
```

Example:

```bash
curl http://localhost:3000/otp/9876543210/ttl
```

Example response while the OTP is active:

```json
{
  "ttl": 24
}
```

The `ttl` value is returned by Redis's `TTL` command and is measured in
seconds. The value decreases as the OTP approaches expiration.

If the key does not exist, Redis returns `-2`:

```json
{
  "ttl": -2
}
```

Redis can also return `-1` for a key that exists without an expiration. The
current application always sets the OTP with an expiration, so an active OTP
normally has a positive TTL and a missing OTP returns `-2`.

## Typical test flow

Request an OTP:

```bash
curl -X POST http://localhost:3000/otp \
  -H "Content-Type: application/json" \
  -d '{"phone":"9876543210"}'
```

Check its TTL:

```bash
curl http://localhost:3000/otp/9876543210/ttl
```

Verify it using the OTP returned by the first request:

```bash
curl -X POST http://localhost:3000/otp/verify \
  -H "Content-Type: application/json" \
  -d '{"phone":"9876543210","otp":"REPLACE_WITH_OTP"}'
```

Check the TTL again. It should now return `-2` because successful verification
deletes the key:

```bash
curl http://localhost:3000/otp/9876543210/ttl
```

To test expiration instead, request an OTP, wait more than 30 seconds, and
then call the verification endpoint. Redis will have removed the key.

## Important implementation notes

- Redis stores values as strings. The verification example should send `otp`
  as a JSON string, such as `"123456"`, because the source compares the Redis
  value with strict equality (`!==`).
- The current source does not validate whether `phone` or `otp` is present.
  Production code should validate the request body and return an appropriate
  client error for missing or invalid values.
- The current source returns the OTP in the HTTP response for demonstration
  purposes. A production application should never expose the OTP in its API
  response or logs.
- The current source does not rate-limit OTP requests or verification attempts.
  A production application should add throttling and an attempt limit.
- `Math.random()` is suitable for this learning example but should be replaced
  with a cryptographically secure random-number generator for production
  authentication flows.
- The phone number is directly included in the Redis key. Production code
  should normalize phone numbers and consider privacy requirements.
- The routes do not define explicit error handling for Redis or server errors.
  Production code should handle connection failures and return consistent
  HTTP status codes.
- The `mongoose` package is present in `package.json`, but this example does
  not connect to MongoDB or use Mongoose.
